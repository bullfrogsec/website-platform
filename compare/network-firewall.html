Bullfrog Egress Control vs network firewalls

An allowed domain is not a data boundary.

AI agents need shared services like GitHub and package registries to do useful work. But allowing a service does not restrict which account they send data to or which operations they perform. An attacker can target a service your agent already uses.

Bullfrog applies your policy to the request, not just its destination. This comparison isolates IP/domain rules, not firewalls with their own L7 inspection.

How they differ

Feature comparison

Feature comparison: IP/domain rules and Bullfrog
Feature IP/domain rules Bullfrog
Destination restrictions IP/domain rulesAllow or block destination IPs or domains BullfrogRestrict destinations and apply request policy
Accounts and repositories within a service IP/domain rulesSame address, no account distinction BullfrogMatch supported request paths and fields to approved accounts

What this means in practice

Same service. Different account.

With IP/domain rules

Your organization’s repository and an attacker’s repository can share github.com. Allowing the domain permits access to both. Address rules alone cannot decide which repository may receive your data.

With Bullfrog

Configure request rules that allow writes to your approved organization and block writes elsewhere. Agents retain useful access to the service without permission to send data to every account on it.

Allow useful reads. Block unauthorized writes.

With IP/domain rules

Downloading a dependency and publishing a package can use the same registry. The destination address does not tell you whether the agent is reading public data or uploading your code.

With Bullfrog

Use request methods, paths and supported fields to distinguish operations. For example, allow package downloads while blocking publishing requests. These are configured service rules, not automatic classification of sensitive data.

One MCP endpoint. Different tools.

With IP/domain rules

Remote MCP tools can share one HTTPS endpoint. Allowing that endpoint does not distinguish a read-only tool from a tool that creates an issue or sends data to another account.

With Bullfrog

Match tool names and arguments in supported remote MCP requests. A configured policy can permit read tools while blocking create_issue or restricting its target repository. This applies to remote MCP traffic, not local stdio tool calls.

Bullfrog complements network controls: keep destination restrictions and add request-level boundaries. Coverage depends on supported tools, TLS stacks, protocols, configured policy and enforcement mode.
